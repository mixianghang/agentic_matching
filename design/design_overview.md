创建一个基于智能体对话的需求匹配系统，以替代传统电商、交友平台、找房平台等需要用户自己或者借助中介的交易撮合系统。 
 
 # 简介 
 
 一个多agent通信系统，每个用户有一个或者多个agent, 来代表用户完成长序列交互任务，例如租房、相亲（人选匹配，选定时间）等活动； 
 
 - 每个agent实际上是用户的一个线上代表，只需要用户阐明需求，例如租房需求或者出租需求，男女相亲需求、 结伴出游或者临时一起打游戏需求， agent通过广播或者多播，来找到产品或者服务提供方，通过多轮对话，来判断是否匹配，匹配的话，协商后续流程，例如相亲中进一步认证信息与协商见面时间与地点；租房中协商价格与起租时间等 
 - Backbone是一个基于大模型的多agent对话系统， 
     - 用户通过user agent (web 聊天窗口、messaging app）来提出并定义需求（通过多轮对话）； 
     - 根据用户需求，服务器端创建“需求处理的agent”, 即一个任务处理的session；区别于传统软件，用户需求不需要是严格定义的东西；匹配机制也不再是死板的，且需要大量用户介入的。 
     - 这些都是借助大模型的对谈来实现的 
     - 当然，每个用户及其agents会有一个持久层与会话层；直到用户标记一个任务为完成之前，该任务一直运行，用户可以查看进展；重要更新（几年找到xx房子与N个匹配的相亲对象），也要主动周期性的告知用户 
     - 聊天所依赖的基础大模型由系统设定，而非用户（除非额外付费）；服务器可以根据负载以及任务复杂度，选择服务器本地的小模型或者大模型api 
 - Backbone之外，是一些典型任务的workflows, agent可以参考并根据用户需求个性化；比如相亲任务要按照一些步骤，但是用户可以加入额外的，比如身份与房产的验证； 
 - 除了backbone (agentic conversation system)以及task-specific workflows, 还有一些组件(tools), 帮助agent来完成workflow中的关键步骤；例如人脸识别；房产的线上认证等；这类组件是可拓展的，其列表可由agent通过本地文件读写系统来读取 
 - 区别于clawbot 
     - clawbot是一个用户端运行的用户助手，而我们的系统主打云端运行，代表用户来持续运行 
 
 # 设计简述 
 - user agents: web/微信公众号/Telegram Bot等 
     - 新请求发起：通过语音或者文字 
     - 任务列表 
     - 每个任务的进展 
     - 和需求满足方直接对谈或者留言 
 - Backbone: 多agent 服务器端通过LLM-based 对话，提供信息 
     - agent1 与agent 2 对谈，共同的context 为 mutual_context, 自身能看到所代表的用户的信息<user1 information》；聊天过程中，根据对方需求以及用户的规定，决定将 user 1 information哪个部分提供给对方 （xxx + yyy) 
     - 基于地理位置等信息的高效但粗略匹配，例如总计N个agents, 匹配后剩余1%在同一个城市，然后做广播匹配 
 - 用户管理：注册、第三方登录（微信）、个性化配置等 
 - 持久层：借助对象存储等技术，持续存储用户、任务等相关信息
